## 1. Problem Statement

Lifting logs show raw numbers such as "3 sets of 5 at 225 lb", which are hard to feel or compare. Lifters, especially those who like visible progress, get no tangible sense of what they have moved. Turning every rep into a boulder, sized by how heavy the lift was, makes progress concrete and motivating: light work produces Pebbles, heavy work produces Monoliths. This is the app's hook and what separates it from generic trackers.

## 2. Goals

- Classify every logged rep into a boulder tier based on the weight lifted for that set.
- Show boulders as counts per tier (a pile) for a session, the last 7 days, and all time, alongside the exact total weight lifted.
- Work fully offline and on-device, with no account.
- Support pounds and kilograms with consistent tier boundaries.
- Keep tiers as data (name and lower bound), so they can be rebalanced without touching logic.

## 3. Non-Goals

- Workout entry UI (belongs to 1.0).
- Alternate views such as one big boulder or a single tier (1.2).
- Accounts, cloud sync, social features or leaderboards.
- Animated or 3D boulder scenes (MVP uses static or lightly animated 2D art).
- Bodyweight, cardio or time-based work (no external weight, so no boulder).
- Health or performance advice.

## 4. Personas & User Stories

- **As a lifter**, I want each rep to become a boulder sized by its weight so that heavy work looks heavy.
- **As a lifter**, I want to see my session as a pile of boulders and my exact total weight so that both the fun view and the real numbers are there.
- **As a lifter using kilograms**, I want the same tiers to apply to my lifts so that I am not treated as second-class.
- **As a new user**, I want to see what weight makes a Pebble or a Monolith so that the tiers make sense.
- **As a developer**, I want tier boundaries in one config so that I can rebalance them without touching logic.

(Instructor, admin, parent and homeschool personas from the template do not apply.)

## 5. Functional Requirements

- **FR-1.** The system MUST treat each logged rep as one boulder, so a set of `reps` at `weight` produces `reps` boulders of one tier.
- **FR-2.** The system MUST assign a tier from the per-rep weight of the set using the table below, with each lower bound inclusive.
- **FR-3.** The system MUST define tiers in a single data table (id, name, `minLb`, art asset), ordered lightest to heaviest.
- **FR-4.** The system MUST return, for a set of logged sets, a boulder count per tier, the total reps counted, and the exact total weight lifted (`sum of reps x weight`).
- **FR-5.** The system MUST support the scopes: single workout, last 7 days, and all time.
- **FR-6.** The system MUST accept weights in lb or kg and classify against the tier table using the exact factor 1 lb = 0.45359237 kg.
- **FR-7.** The system MUST exclude sets with a weight of 0 or less, or 0 reps, from boulder counts, and MUST NOT error on them.
- **FR-8.** The system MUST display a text equivalent of the pile (for example "15 Great Boulders, 24 Boulders, 30 Stones, 36 Pebbles") and the exact total.
- **FR-9.** The system SHOULD cap the number of drawn icons per tier (for example 20) and collapse the rest into a "x N" label.
- **FR-10.** The system SHOULD let the user tap a tier to see its weight range in their preferred unit.
- **FR-11.** The system MAY show a highlight when a logged set is the heaviest tier the user has ever lifted.

### Tier table (lower bound inclusive, weight of one lift)

| Tier | Per-rep weight (lb) | Range as read from the request |
|---|---|---|
| Pebble | under 10 | greater than 0 and under 10 |
| Stone | 10 to under 50 | "10+ through 50" |
| Rock | 50 to under 100 | "50-99" |
| Boulder | 100 to under 200 | "100" |
| Great Boulder | 200 to under 300 | "200" |
| Monolith | 300 and up | "300+" |

Boundary decisions: exactly 50 lb counts as a Rock (the request listed 50 in both Stone and Rock; lower-bound-inclusive was chosen). Boulder and Great Boulder were given as single values, so they are read as starting points that run up to the next tier.

## 6. Non-Functional Requirements

- **Performance** — classifying 100,000 logged sets completes in under 50 ms on a mid-range phone; the UI renders in under 100 ms once data is loaded.
- **Security** — no network calls, no secrets, no third-party scripts in MVP.
- **Privacy & Compliance** — all data stays on the device (IndexedDB). No PII collected. Revisit if accounts or analytics are added.
- **Accessibility** — WCAG 2.1 AA: the text summary is the primary source of truth, the pile graphic has an accessible name and description, and colour is never the only signal.
- **Scalability** — local-only; keep a cached all-time tier count and total that updates on each new set, so the all-time view does not rescan every set.
- **Reliability** — classification is a pure function (same input, same output). Weight is stored as integer grams. Tier thresholds are converted to grams with the same rounding function used to store weights, so a lift entered as exactly 100 lb is never classified as under 100 lb.
- **Observability** — dev-only console logging of classification inputs and outputs; no telemetry in MVP.
- **Maintainability** — classification logic lives in one module with no UI or storage imports.
- **Internationalization** — tier names and strings externalised; lb/kg toggle; number formatting follows locale.
- **Backward compatibility** — boulders are derived at read time and never persisted, so changing tier bounds re-buckets old workouts without a migration (see Open Question 4).

## 7. Acceptance Criteria

- **AC-1.** *Given* 3 sets of 5 reps at 225 lb, 3 sets of 8 at 135 lb, 3 sets of 10 at 25 lb and 3 sets of 12 at 8 lb *When* converted *Then* the result is 15 Great Boulders, 24 Boulders, 30 Stones and 36 Pebbles (105 boulders) and a total weight of 7,653 lb.
- **AC-2.** *Given* single-rep weights of 9.99, 10, 49.99, 50, 99.99, 100, 199.99, 200, 299.99 and 300 lb *When* classified *Then* the tiers are Pebble, Stone, Stone, Rock, Rock, Boulder, Boulder, Great Boulder, Great Boulder, Monolith.
- **AC-3.** *Given* a lift entered as exactly 100 lb, and another as 45.359 kg *When* classified *Then* both are Boulders (no rounding error drops them to Rock).
- **AC-4.** *Given* a lift of 4.5 kg (about 9.92 lb) and one of 4.54 kg (about 10.01 lb) *When* classified *Then* the first is a Pebble and the second is a Stone.
- **AC-5.** *Given* a set with 0 lb weight or 0 reps *When* counted *Then* it adds no boulders and causes no error.
- **AC-6.** *Given* no logged sets *When* the view opens *Then* an empty state explains how to log a workout, with no errors.
- **AC-7.** *Given* a screen reader user *When* the view loads *Then* the text summary is announced and the graphic does not add duplicate noise.
- **AC-8.** *Given* the device is offline *When* the app is opened *Then* the boulder view works normally.

(AC-1 and AC-2 expected values were checked with a quick script against the tier table.)

## 8. Data Model

Local-only, so no SQL migrations. Storage is IndexedDB via a thin wrapper.

- `sets` (from 1.0): `id`, `workoutId`, `exerciseId`, `reps` (int), `weightGrams` (int, weight per rep), `loggedAt` (ISO string).
- `settings`: `unit` (`lb` | `kg`, default `lb`).
- Index on `loggedAt` for the 7-day scope; `workoutId` for the single-workout scope.
- Derived, not stored: tier per set, counts per tier, total weight.
- Optional cache: all-time `countsByTier` and `totalGrams`, rebuilt from `sets` at any time.
- Backfill: none (new app).
- Tier table lives in `src/config/tiers.ts`, e.g. `{ id: "stone", minLb: 10 }`. Thresholds in grams are computed once at load with the same rounding as weight storage.

## 9. API Surface

No HTTP routes in MVP (local-only). Internal module contract:

```ts
type Tier = { id: string; nameKey: string; minLb: number; art: string };
type BoulderResult = {
  countsByTier: { tierId: string; count: number }[]; // lightest to heaviest
  totalBoulders: number;
  totalGrams: number;
};
function tierForWeight(weightGrams: number, tiers: Tier[]): string | null; // null if weight <= 0
function toBoulders(sets: SetRecord[], tiers: Tier[]): BoulderResult;
```

If accounts are added later, expose `GET /api/v1/me/boulders?scope=` with the same shape and OpenAPI docs.

## 10. UI / UX

- **New page:** Boulders (home tab), with a scope switcher (Workout / 7 days / All time).
- **New components:** `BoulderPile`, `TierLegend`, `BoulderSummary`.
- **Key flows:**
  1. User finishes logging a set, then taps Boulders.
  2. App shows the pile for the chosen scope with the text summary and exact total weight.
  3. User taps a tier to see its weight range in their unit.
  4. User switches scope to compare session vs lifetime.
- **States:** empty (no sets), loading (skeleton), error (storage unavailable, with retry), offline (no change).
- **Responsive:** mobile-first single column; the pile scales, with icons capped per FR-9.
- **Accessibility:** heading order, visible focus on tier buttons, `aria-label` on the graphic, respect `prefers-reduced-motion`.
- **i18n keys:** `tier.pebble`, `tier.stone`, `tier.rock`, `tier.boulder`, `tier.greatBoulder`, `tier.monolith`, `boulders.summary`, `boulders.total`, `boulders.empty`.

## 14. Risks & Mitigations

| Risk | Likelihood | Impact | Mitigation |
|---|---|---|---|
| Rounding errors at tier boundaries (lb vs kg) | M | M | Integer grams; thresholds rounded with the same function; boundary tests (AC-2, AC-3, AC-4) |
| Many reps of light weight produce huge Pebble counts that drown out heavy work | M | M | Show counts per tier plus the exact total; consider a weighted view later (Open Question 2) |
| Users with metric plates find lb-based tiers odd (4.5 kg is a Pebble, 4.54 kg a Stone) | M | M | Show ranges in the user's unit; decide on metric-native bounds (Open Question 3) |
| Pile graphic cluttered at high counts | M | L | Cap icons per tier (FR-9), collapse to "x N" |
| Data loss from clearing browser storage | M | H | Add export/import in a later feature; warn in settings |
| Copyright or trademark issues with boulder art | L | M | Use original or licensed art only |

## 15. Rollout Plan

- **Feature flag:** `boulders_enabled`, default ON in dev, OFF until the acceptance criteria pass.
- **Sequencing:** tier config, then classification module and tests, then UI, then flip the flag.
- **Dogfood:** you and a few classmates or friends log a week of workouts and sanity-check the tiers.
- **GA criteria:** all ACs pass, axe reports no serious violations, works offline.
- **Rollback:** turn the flag off; no data migration to reverse since results are derived.

## 16. Test Plan

- **Unit** — `tierForWeight` at every boundary (9.99/10, 49.99/50, 99.99/100, 199.99/200, 299.99/300), zero and negative weights, lb vs kg equivalence, `toBoulders` totals for AC-1.
- **Integration** — IndexedDB reads for each scope; 7-day window edge cases (timezone, midnight); cache rebuild matches a full rescan.
- **End-to-end** — Playwright: log sets, open Boulders, verify summary text and total, switch scope and unit, go offline.
- **Security** — confirm no network requests are made; check for XSS in any user-entered exercise names displayed.
- **Accessibility** — automated axe run; manual screen-reader pass on the summary and tier buttons.
- **Performance / load** — synthetic 100,000-set dataset; classification under 50 ms.
- **Manual exploratory** — very large weights, decimal weights, unit toggle mid-session, small screens.

## 18. Open Questions

1. **Are these bounds right for your users?** A 300 lb Monolith is a heavy squat or deadlift, which is realistic for barbell work but rare for dumbbells. Defend or adjust: should an average lifter ever see a Monolith?
2. **Should heavy work count more than many light reps?** 36 Pebbles (lateral raises) look as numerous as 36 Monoliths would. Is a plain count fair, or should the pile be weighted?
3. **Metric-native bounds?** Keep lb-defined bounds shown in kg, or define a separate kg table (for example Pebble under 5 kg, Stone 5 kg, Rock 25 kg, Boulder 50 kg, Great Boulder 100 kg, Monolith 150 kg)?
4. **Should changing tiers re-bucket history?** Deriving at read time re-buckets old workouts if bounds change. Is that desired, or should bounds be versioned?
5. **Warm-up sets and drop sets:** count them, or let the user mark sets as warm-up so they are excluded?
6. **Bodyweight work:** excluded in MVP. Should push-ups or pull-ups count (for example as a fixed Pebble)?
7. **Feature ID and stack:** 1.1 assumes 1.0 is Workout Logging and a TypeScript web app with IndexedDB; confirm before implementation.
